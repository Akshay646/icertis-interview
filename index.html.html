What the reported experiences agree on, so you know what each round is actually probing.

What does each round actually test?

The three rounds are not three difficulty levels of the same thing. They probe different claims you have made.

L1 — do you own the platform

Questions from .NET, C#, LINQ and SQL. One reported account puts it bluntly: they check whether the basics are strong or not. Expect definition-then-why chains: what is an assembly, then what types, then why does that matter at deployment. Level 1 coding questions appear here too.

L2 — did you really build what the resume says

Current project architecture and design patterns. Scenario-based rather than quiz-based. The common pattern is a production incident, a design pattern you claim to have used, or a scaling decision. They are checking that your project story survives contact with specifics.

HR — fit, expectations, and compensation

Reported as professional and clear about role, culture, and expectations. This is a real round, not a formality.

The highest-leverage preparation

Every reported L2 round anchors on your own project. Prepare one architecture you can draw on a whiteboard in ninety seconds, with two decisions you can defend and one you would now make differently.

C# & .NET fundamentals

6 questions

Directly reported: assemblies and their types, C++ interop, .NET Framework questions, and general “are the basics strong” probing.

What is an assembly in .NET, and what are its types?

An assembly is the unit the runtime actually loads. It is the fundamental unit of deployment, versioning, reuse, activation scoping and security permissions, and it ships as a .dll or .exe. To the runtime, a type does not exist outside the context of an assembly.

What is inside one

  • Manifest — assembly name, version, culture, strong-name key, and the list of files and referenced assemblies.
  • Type metadata — every type and member, which is what reflection and the debugger read.
  • IL — the compiled intermediate language, JIT-compiled to machine code on first call.
  • Resources — embedded strings, images, satellite data.

The follow-up that catches people

“Does the GAC exist in .NET Core?” No. The GAC and multi-file assemblies are .NET Framework concepts. Modern .NET resolves dependencies per-application through NuGet and the deps file, which is precisely what killed DLL hell. If you answer the question purely in Framework terms, expect this next.

Can we use existing C++ code in a .NET application?

Yes, and there are four routes. Pick based on what the C++ actually is, and say why you picked it — that is the real question.

1. P/Invoke — for a flat C-style exported API

Declare the native function in managed code and let the runtime marshal the call. This is the standard answer.

using System.Runtime.InteropServices;

internal static partial class Native
{
    [LibraryImport("geometry.dll", StringMarshalling = StringMarshalling.Utf8)]
    internal static partial double ComputeVolume(double length, double width, double height);
}

LibraryImport is the source-generated form on modern .NET; DllImport is the older attribute and still works. The C++ side must export with extern "C" to avoid name mangling.

2. C++/CLI — for a real C++ class library

A mixed-mode wrapper project that can hold both managed and native types, so you expose a .NET-shaped class and hold the native object inside. Expensive to maintain and Windows-only, which is the trade-off to mention.

3. COM interop — if the C++ is already a COM component

Add a reference, the runtime generates the interop assembly, and you call it like a .NET object.

4. Out-of-process — if the native code is unstable or GPL-awkward

Run it as a separate process or service and talk over gRPC, a pipe or a queue. Slower per call, but an access violation in the native code kills that process rather than your web app.

What they want to hear

That you know the costs: marshalling overhead on every crossing, no GC over native memory so ownership must be explicit, a native crash takes down the whole process, and you must match bitness — a 32-bit DLL will not load into a 64-bit worker process.

Managed vs unmanaged code, CLR, IL and JIT — walk through what happens to your code
  1. The C# compiler (Roslyn) produces IL plus metadata, packaged into an assembly. It does not produce machine code.
  2. At runtime the CLR loads the assembly and the JIT compiles each method to native code the first time it is called, caching the result for subsequent calls.
  3. The CLR provides garbage collection, type safety, exception handling and security. Code running under it is managed.
  4. Unmanaged code — a C++ DLL, a COM object — runs outside that, with its own memory management.

Tiered compilation means hot methods get re-jitted at a higher optimisation level after they have proven themselves, so startup is fast and steady-state is fast. ReadyToRun and AOT move some or all of that work to build time.

Likely follow-up

“How does the GC know what to collect?” Generational mark-and-sweep: gen 0 for new short-lived objects collected often and cheaply, survivors promoted to gen 1 and gen 2, and a separate Large Object Heap for allocations over 85,000 bytes. Mention that IDisposable and using exist for unmanaged resources, which the GC does not know how to release.

Reference Common Language Runtime — Microsoft Learn Garbage collection fundamentals
Value types vs reference types, and where each lives

Value types hold the data; reference types hold the address of the data.

  • Value — struct, enum, and primitives. Copied on assignment. Usually on the stack, but a value type that is a field of a class lives on the heap inside that object.
  • Reference — class, interface, delegate, array, string. The variable is on the stack, the object on the heap.

Boxing wraps a value type in a heap object so it can be treated as object; unboxing extracts it. Both cost an allocation and a copy, which is why generic collections replaced ArrayList.

Classic trap

“Strings are reference types, so are they mutable?” No — string is a reference type that is immutable. Every concatenation allocates a new string, which is why StringBuilder exists for loops. Expect this to be asked as a trick.

Reference Value types — C# reference
What is a delegate, and how do events build on it?

A delegate is a type-safe function pointer — a type whose instances hold a reference to a method with a matching signature. Func<T,TResult>, Action<T> and Predicate<T> are the built-in generic ones, and LINQ is built on them.

An event is a delegate field with restricted access: outside the declaring type you can only += and -=, not assign or invoke. That restriction is the whole point — a subscriber cannot wipe out other subscribers or raise the event itself.

public event EventHandler<StatusChangedEventArgs> StatusChanged;

protected virtual void OnStatusChanged(StatusChangedEventArgs e)
    => StatusChanged?.Invoke(this, e);   // null-conditional: no subscribers is legal
Follow-up worth pre-empting

Event handlers are a common managed memory leak: a long-lived publisher holding a reference to a short-lived subscriber keeps the subscriber alive. Always unsubscribe, or the GC cannot collect it.

OOP & SOLID

4 questions

Reported as “OOPS implementations”, “SOLID principles” and “abstraction” across multiple rounds. The word implementations matters — they want code, not definitions.

Explain the four OOP pillars — with how each is implemented in C#

Definitions alone score nothing. Attach each to a language feature and a reason.

Encapsulation

State is private; change goes through methods that can enforce invariants. Implemented with access modifiers, properties, and readonly fields. The reason: an object that cannot be put into an invalid state is one you do not have to defend against everywhere else.

Abstraction

Expose what the caller needs, hide how it is done. Implemented with interfaces and abstract classes. In your integration platform this is literally the product: callers see one service contract, the vendor-specific mess sits behind it.

Inheritance

An “is-a” relationship reusing a base implementation. Implemented with : BaseClass, virtual and override. Use sparingly — composition is usually the better default.

Polymorphism

  • Compile-time (overloading) — same name, different parameters, resolved by the compiler.
  • Runtime (overriding) — virtual / override, resolved through the vtable at execution.
Interface vs abstract class — asked almost every time

An abstract class models an “is-a” with shared state and implementation; a class can have only one. An interface is a contract with no state; a class can implement many. Since C# 8, interfaces can carry default implementations — so if you say “interfaces cannot have implementations”, expect to be corrected. The real rule stands anyway: interfaces still cannot hold instance state.

Reference Object-oriented programming in C# — Microsoft Learn
Abstraction vs encapsulation — they sound the same, so what is the difference?

This is asked specifically to see whether you have memorised or understood.

  • Abstraction is about design — deciding what to expose. It happens when you define the interface. It solves complexity.
  • Encapsulation is about enforcement — hiding how the internals work and guarding them. It happens when you choose access modifiers. It solves integrity.

One sentence that lands: abstraction removes decisions the caller should not have to make; encapsulation removes access the caller should not have.

public interface IDocumentStore              // abstraction: the what
{
    Task<Uri> UploadAsync(Stream content, string path);
}

public sealed class AccDocumentStore : IDocumentStore
{
    private readonly HttpClient _http;       // encapsulation: the how, locked away
    private string? _cachedToken;

    public async Task<Uri> UploadAsync(Stream content, string path) { /* ... */ }
}

The caller cannot reach _cachedToken (encapsulation) and does not know the store is ACC at all (abstraction).

Walk through SOLID with a real violation and fix for each

S — Single responsibility

A class has one reason to change. A controller that validates, maps, calls the vendor API and writes audit rows has four. Split into validator, mapper, client and audit sink.

O — Open/closed

Open to extension, closed to modification. A switch over vendor type that you edit for every new vendor is the violation; a registered set of IVendorClient implementations resolved by key is the fix.

L — Liskov substitution

A subtype must be usable anywhere the base is. The textbook violation is a derived class that throws NotSupportedException on an inherited method — a read-only collection inheriting a mutable one. If a caller has to check the concrete type, you broke it.

I — Interface segregation

No client should depend on methods it does not use. A fat IRepository with twenty methods forces every implementation and every test double to deal with all of them. Narrow interfaces per use case instead.

D — Dependency inversion

High-level modules depend on abstractions, not concretions. The service takes IDocumentStore, not AccDocumentStore. This is what makes ASP.NET Core’s built-in container useful rather than ceremonial.

The strong answer

Pick one and tell a real story — where you felt the pain, what you changed, what it cost. A candidate who recites five definitions sounds like everyone. A candidate who says “our vendor switch statement was an open/closed violation and here is what it cost us on the third integration” sounds like an engineer.

Design patterns

4 questions

Reported in three separate accounts, including the direct question “which design pattern was used in your project”. That one is about your project, not the Gang of Four.

Which design pattern was used in your project?

This is the highest-risk question in the set, because the wrong answer is easy to give. Naming a pattern you did not deliberately choose invites a follow-up you cannot answer.

Answer in four beats

  1. The problem — what was painful before.
  2. The pattern — named, correctly.
  3. The implementation — the actual types involved.
  4. The cost — what it made worse, because everything does.

A worked example from an integration platform

Problem: several products each integrated directly with vendor APIs, so a vendor contract change meant edits in every consumer.

Pattern: Adapter behind a Strategy, resolved by a Factory. Each vendor gets an adapter implementing one internal contract; the factory resolves the right adapter per tenant configuration.

Implementation: IVendorClient as the contract, one implementation per vendor registered by key, resolved at runtime from the tenant’s stored configuration.

Cost: the shared contract becomes a lowest common denominator. When one vendor exposes a capability the others do not, you either leak it through the abstraction or lose it. That tension is real and saying so is what makes the answer credible.

Patterns you have almost certainly used without naming them

Repository and Unit of Work (DbContext is both), Dependency Injection, Options, Middleware chain (Chain of Responsibility), Mediator if you use MediatR, Decorator for caching or retry layers, Factory for anything resolved by key. Scan your own codebase before the interview and pick two you can defend.

Singleton — implement it thread-safely, and say when not to use it

The canonical C# implementation uses Lazy<T>, which is thread-safe by default:

public sealed class ConnectionRegistry
{
    private static readonly Lazy<ConnectionRegistry> _instance =
        new(() => new ConnectionRegistry());

    public static ConnectionRegistry Instance => _instance.Value;

    private ConnectionRegistry() { }   // private ctor: no outside construction
}

The older double-checked locking version with a volatile field is worth knowing because interviewers still ask for it, but Lazy<T> is what you would ship.

The answer that separates seniors

In a modern ASP.NET Core app you almost never hand-roll a singleton — you register the type with AddSingleton and let the container own the lifetime. That keeps it testable and injectable, whereas a static Instance property is a hidden global dependency you cannot substitute in a test. Say this. It shows you know the pattern and why the framework superseded the hand-rolled form.

Is Repository still worth it on top of EF Core?

A genuinely contested question, and interviewers ask it to see whether you hold a view or recite a rule.

The case against: DbContext already is a Unit of Work and DbSet<T> already is a repository. Wrapping them usually produces a thin pass-through that leaks IQueryable anyway, and any repository that returns IQueryable has abstracted nothing.

The case for: it gives a seam for testing without a database, concentrates complex query logic in one place, and keeps provider-specific behaviour out of the domain.

The defensible position: do not add a generic IRepository<T> over everything. Do add focused, intention-revealing abstractions where a query is genuinely complex or reused. Name the methods after what the domain means, not after CRUD.

Async & concurrency

3 questions

Reported directly as “Async”. In .NET rounds this is reliably where candidates who have only used async by copying surrounding code get found out.

What actually happens when you await something?

The key insight, and the one they are testing: async is about releasing the thread, not about using more threads.

  1. The method runs synchronously until the first await.
  2. If the awaited task is already complete, execution just continues — no suspension, no cost.
  3. If not, the compiler-generated state machine registers a continuation and returns the thread to the pool. No thread is blocked waiting.
  4. When the I/O completes, the continuation is scheduled and the rest of the method runs — possibly on a different thread.

For a web server that is the whole point: a thread parked on a database call is a thread not serving another request. Async I/O is what lets a small thread pool serve high concurrency.

Why does .Result or .Wait() deadlock, and what is ConfigureAwait(false) for?

A classic question, and one with a version-dependent answer — say both halves.

The deadlock

In a framework with a synchronisation context that allows only one thread at a time — classic ASP.NET and WinForms/WPF — this sequence deadlocks:

  1. A request thread calls SomethingAsync().Result and blocks, holding the context.
  2. The async method completes and tries to resume on the captured context.
  3. The context is occupied by the blocked thread. Each waits for the other. Forever.

ConfigureAwait(false) tells the continuation not to resume on the captured context, which breaks the cycle.

The modern nuance that earns the point

ASP.NET Core has no synchronisation context, so this particular deadlock does not occur there. But blocking on async code is still wrong — it burns a pool thread for the duration and can cause pool starvation under load. ConfigureAwait(false) remains correct practice in library code, where you do not control the caller’s context. The rule to state: async all the way down, and never block on async.

Task vs Thread, and when do you actually want Task.Run?
  • A Thread is an OS resource, roughly a megabyte of stack, expensive to create.
  • A Task is a promise of a future result, usually serviced by the thread pool, and may not involve a dedicated thread at all.

Task.Run pushes work onto a pool thread. It is right for CPU-bound work you want off the current thread — in a desktop app, off the UI thread. It is wrong for I/O: wrapping a database call in Task.Run does not make it asynchronous, it just occupies a pool thread while the original one waits.

// Wrong: burns a pool thread, achieves nothing
var rows = await Task.Run(() => db.Elements.ToList());

// Right: true async I/O, no thread held
var rows = await db.Elements.ToListAsync(ct);
Related terms worth having ready

Parallel.ForEachAsync for bounded concurrent work, SemaphoreSlim to throttle it, CancellationToken threaded through every async call, and IAsyncEnumerable<T> for streaming results rather than buffering them.

LINQ

3 questions

Named explicitly in the L1 round and again in a second account. Deferred execution is the question that comes up most.

Deferred vs immediate execution — when does a LINQ query actually run?

Building a query does nothing. The query runs when you enumerate it.

  • Deferred — Where, Select, OrderBy, Take, Skip, GroupBy. These return a new query object.
  • Immediate — ToList, ToArray, Count, First, Single, Any, Sum, Max. These force enumeration now.

The consequence people get caught by: a deferred query re-executes every time you enumerate it. Against a database that is a round trip per enumeration.

The classic gotcha

A deferred query captures variables, not values. Modify the filter variable after building the query and before enumerating it, and the query uses the new value. Materialise with ToList() when you want the result frozen.

IEnumerable vs IQueryable — why does it matter so much with a database?

This single distinction is responsible for a large share of real .NET performance incidents.

IEnumerable<T>IQueryable<T>
HoldsA delegateAn expression tree
Filtering happensIn memory, in your processIn the database, translated to SQL
Data transferredEverything, then filteredOnly matching rows
// Disaster: AsEnumerable() pulls the whole table into memory first
var recent = db.Documents.AsEnumerable()
                .Where(d => d.CreatedUtc > cutoff)
                .ToList();

// Correct: Where is translated into the SQL WHERE clause
var recent = await db.Documents
                .Where(d => d.CreatedUtc > cutoff)
                .ToListAsync(ct);

Returning IEnumerable<T> from a repository method silently does the same thing — every caller’s filter runs in memory. That is the practical argument against leaky repository abstractions.

Related trap

Count() > 0 versus Any(). Any() stops at the first match; Count() counts everything. On a large table that is the difference between SELECT TOP 1 and a full count.

Entity Framework

3 questions

Reported as “EF” and “EF performance”. In practice this round is almost always about N+1 and tracking.

What is the N+1 problem, and how do you fix it?

One query to fetch N parents, then one more query per parent to fetch its children. Fifty parents means fifty-one round trips — each with network latency, each holding a connection.

// N+1: lazy loading fires a query per iteration
var projects = await db.Projects.ToListAsync(ct);
foreach (var p in projects)
    Console.WriteLine(p.Documents.Count);   // one SELECT per project

// Fixed: one round trip
var projects = await db.Projects
    .Include(p => p.Documents)
    .ToListAsync(ct);
Round trips: lazy loading vs Include
50

When Include is not the answer

A single query with several Includes on one-to-many relationships produces a cartesian explosion — the parent columns are duplicated across every child row. EF Core calls this cartesian explosion and offers AsSplitQuery(), which loads the related collections with separate queries instead. Trade-off: more round trips, far less duplicated data. Knowing both sides of this is a strong signal.

Reference Efficient querying — EF Core docs Single vs split queries
What does AsNoTracking do, and when should you use it?

By default EF Core tracks every entity it materialises, keeping a snapshot so SaveChanges can work out what changed. That costs memory and CPU proportional to the result set.

AsNoTracking() skips it. For a read-only query — any GET endpoint, any report — it is free performance and should be the default.

var rows = await db.Elements
    .AsNoTracking()
    .Where(e => e.LevelId == levelId)
    .Select(e => new ElementDto(e.Id, e.Name, e.Category))   // project, do not materialise entities
    .ToListAsync(ct);

The Select matters as much as the tracking. Projecting to a DTO means the generated SQL selects only those columns, instead of every column of the table.

Full EF performance checklist

AsNoTracking for reads · project with Select rather than returning entities · AsSplitQuery when includes multiply rows · paginate with keyset rather than large Skip · batch writes rather than saving in a loop · compiled queries for very hot paths · and always read the generated SQL before deciding anything.

Reference Change tracking — EF Core docs
Lazy, eager and explicit loading — which, and why
  • Eager (Include) — fetch related data up front, in the same query. Predictable. The default choice when you know you need the children.
  • Explicit (Entry(...).Collection(...).LoadAsync()) — fetch on demand, but visibly, in code you wrote.
  • Lazy — fetch automatically on property access, via proxies. Convenient and the usual cause of accidental N+1, because the queries are invisible at the call site.

The position to hold: lazy loading is off by default in EF Core for a reason, and in a web API it should generally stay off. A query firing inside a serialisation loop is a production incident waiting to happen.

SQL

4 questions

Reported in three accounts: nth highest salary with conditions, performance tuning, and general SQL in the L1 round.

Write a query to find the nth highest salary — with conditions

Interviewers ask this because there are four valid answers and the differences between them are where the real discussion is.

1. DENSE_RANK — the answer to give first

WITH Ranked AS (
    SELECT EmployeeId, Name, DepartmentId, Salary,
           DENSE_RANK() OVER (ORDER BY Salary DESC) AS rnk
    FROM   Employees
    WHERE  IsActive = 1            -- the "with some conditions" part
)
SELECT EmployeeId, Name, Salary
FROM   Ranked
WHERE  rnk = @n;

2. Nth highest per department — the usual follow-up

Add PARTITION BY. This is the modification they are driving at, so have it ready:

WITH Ranked AS (
    SELECT EmployeeId, Name, DepartmentId, Salary,
           DENSE_RANK() OVER (PARTITION BY DepartmentId ORDER BY Salary DESC) AS rnk
    FROM   Employees
    WHERE  IsActive = 1
)
SELECT DepartmentId, EmployeeId, Name, Salary
FROM   Ranked
WHERE  rnk = @n
ORDER  BY DepartmentId;

3. OFFSET/FETCH — only correct without ties

SELECT DISTINCT Salary
FROM   Employees
ORDER  BY Salary DESC
OFFSET @n - 1 ROWS FETCH NEXT 1 ROWS ONLY;

4. Correlated subquery — the classic, and the slow one

SELECT MIN(Salary) FROM (
    SELECT DISTINCT TOP (@n) Salary FROM Employees ORDER BY Salary DESC
) AS t;
RANK vs DENSE_RANK vs ROW_NUMBER — say this unprompted

With salaries 100, 90, 90, 80: ROW_NUMBER gives 1,2,3,4 — arbitrary among ties. RANK gives 1,2,2,4 — it skips. DENSE_RANK gives 1,2,2,3 — no gaps. So “3rd highest salary” means 80 under DENSE_RANK and nothing at all under RANK. Stating which semantics you chose, and why, is the entire point of the question.

How do you approach SQL performance tuning?

Answer as a process, not a list of tricks. A process is what a senior is being hired for.

1. Find the actual offender

Query Store on SQL Server gives you historical regressed queries, execution counts and resource use. Without it you are guessing. Also look at wait statistics — they tell you whether you are blocked on CPU, I/O or locks, and those three have different fixes.

2. Read the execution plan

The things to look for: clustered index scan where you expected a seek, key lookups repeated many times, a warning triangle for implicit conversion, and a large gap between estimated and actual rows, which usually means stale statistics or a non-sargable predicate.

3. Fix the common causes in order

  • Non-sargable predicates — WHERE YEAR(CreatedUtc) = 2026 cannot use an index. Rewrite as a range: >= '2026-01-01' AND < '2027-01-01'.
  • Implicit conversion — an nvarchar parameter against a varchar column forces a scan. Match the types.
  • Missing covering index — add the filter columns as keys and the selected columns as INCLUDE to remove key lookups.
  • SELECT * — defeats covering indexes and moves columns nobody reads.
  • Parameter sniffing — one plan cached for a skewed parameter. OPTIMIZE FOR UNKNOWN, RECOMPILE, or fix the statistics.

4. Verify, then stop

Measure after the change with the same tooling. An index that fixes a read and slows every write is a loss you must be able to see.

Clustered vs non-clustered — asked as a sub-question

A clustered index is the table, sorted by its key — one per table. A non-clustered index is a separate structure with a pointer back, so it may need a key lookup to fetch columns it does not cover. That lookup is why covering indexes matter.

Joins, and the ones people get wrong
  • INNER — rows matching on both sides.
  • LEFT — all left rows, nulls where the right has no match.
  • RIGHT — the mirror, rarely used because a LEFT reads better.
  • FULL OUTER — everything from both, nulls where unmatched.
  • CROSS — cartesian product. Deliberate in a calendar table, a bug everywhere else.
  • CROSS / OUTER APPLY — a correlated join against a table-valued expression. The right answer for top-N-per-group.
The trap

Putting a condition on the right table in the WHERE clause of a LEFT JOIN silently converts it to an INNER JOIN, because NULL = anything is not true. If you want to filter the right side and keep unmatched left rows, the condition belongs in the ON clause.

ACID, isolation levels, and what causes a deadlock

ACID: Atomicity — all or nothing. Consistency — constraints hold before and after. Isolation — concurrent transactions do not corrupt each other. Durability — committed means survived a crash.

Isolation levelPreventsStill allows

Read Committed (default)Dirty readsNon-repeatable reads, phantoms

A deadlock is two transactions each holding a lock the other needs. SQL Server detects the cycle and kills the cheaper one as the victim. Prevention: access tables in a consistent order everywhere, keep transactions short, avoid user interaction inside one, and consider READ_COMMITTED_SNAPSHOT to stop readers blocking writers. On the application side, retry the victim — a deadlock victim is a transient fault, not a bug to escalate.

What is a JWT, what is inside it, and how do you validate one?

Three base64url segments separated by dots: header.payload.signature.

{ "alg": "RS256", "typ": "JWT", "kid": "a1b2c3" }        // header
{ "iss": "https://id.example.com", "aud": "civit-api",
  "sub": "user-42", "exp": 1790000000, "tid": "tenant-7" }  // payload (claims)
// signature = RS256( base64url(header) + "." + base64url(payload), privateKey )

Validation — every item matters

  1. Signature against the issuer’s published key from the JWKS endpoint, selected by kid.
  2. Algorithm — against an allow-list. Never trust the token’s own alg; alg: none is a historical vulnerability for exactly this reason.
  3. Issuer (iss) and audience (aud) — a valid token for a different API must be rejected.
  4. Expiry (exp, nbf) with minimal clock skew.
Say this plainly

A JWT is signed, not encrypted. Anyone holding it can read the payload. Never put anything secret in claims. The common follow-up — “how do you revoke one?” — has an honest answer: you largely cannot, which is why access tokens are short-lived and revocation is handled at the refresh token. If you need immediate revocation, you need a reference token and introspection instead.

Reference RFC 7519 — JSON Web Token Authentication in ASP.NET Core
How do you store third-party tokens safely in a multi-tenant service?

This maps directly onto work you own, so expect it to be pulled from your project description rather than asked abstractly.

  • Never expose provider tokens to the browser. The client holds a session identifier; the server exchanges it for the real token. A token that never reaches the client cannot be exfiltrated from it.
  • Encrypt at rest with a key held outside the database, and keep a key version alongside the ciphertext so rotation does not orphan old rows.
  • Validate ownership on every call — the tenant in the token must match the tenant that owns the record. Tenant isolation enforced in code, not implied by routing.
  • Serialise refresh. Concurrent requests hitting an expired token will all try to refresh; without a distributed lock most providers invalidate the losing refresh tokens and you get cascading failures.
  • Log the identifier, never the token. Structured logs get shipped, indexed and read by people.
Anticipate the question under the question

“Where does the encryption key live?” is the real test. Encryption with the key next to the connection string in config buys nothing. The acceptable answers are a managed key service, platform key storage, or at minimum an environment-scoped secret with a rotation story.

DSA & coding problems

Stock buy and sell — maximum profit

One transaction: buy once, sell once, sell must come after buy. The naive answer is every pair, which is O(n²). The expected answer is one pass.

Insight: at each price, the best profit if you sell today is today’s price minus the cheapest price seen so far. Track that minimum as you go.

public static int MaxProfit(int[] prices)
{
    if (prices is null || prices.Length < 2) return 0;

    int minSoFar = prices[0];
    int best     = 0;

    for (int i = 1; i < prices.Length; i++)
    {
        best     = Math.Max(best, prices[i] - minSoFar);
        minSoFar = Math.Min(minSoFar, prices[i]);
    }
    return best;   // 0 if prices only fall — no trade beats not trading
}

Time O(n), space O(1).

Step through the single pass
Follow-ups to have ready

Unlimited transactions: sum every positive day-to-day difference — greedy, still O(n). At most two transactions: track four running states (best after first buy, first sell, second buy, second sell). With a cooldown or fee: same state-machine shape. Saying “this generalises to a state machine over transactions” is the senior-sounding answer.

Iterative — what to write

public static IEnumerable<long> Fibonacci(int count)
{
    long a = 0, b = 1;
    for (int i = 0; i < count; i++)
    {
        yield return a;
        (a, b) = (b, a + b);   // tuple swap: no temp variable
    }
}

O(n) time, O(1) space. The yield return makes it lazy, which is a small signal that you know the language.

Naive recursion — know why it is wrong

static long Fib(int n) => n < 2 ? n : Fib(n - 1) + Fib(n - 2);   // O(2^n)

It recomputes the same subproblems exponentially. Fib(45) takes seconds. Memoisation or a bottom-up table fixes it to O(n) — this is the standard introduction to dynamic programming, and saying so shows you know why the naive version is the teaching example.

Palindrome check, two pointers, O(1) space

public static bool IsPalindrome(string s)
{
    int i = 0, j = s.Length - 1;
    while (i < j)
    {
        if (!char.IsLetterOrDigit(s[i])) { i++; continue; }
        if (!char.IsLetterOrDigit(s[j])) { j--; continue; }
        if (char.ToLowerInvariant(s[i]) != char.ToLowerInvariant(s[j])) return false;
        i++; j--;
    }
    return true;
}

First non-repeating character

public static char? FirstUnique(string s)
{
    var counts = new Dictionary<char, int>();
    foreach (var c in s) counts[c] = counts.GetValueOrDefault(c) + 1;
    foreach (var c in s) if (counts[c] == 1) return c;
    return null;
}

Anagram check

Sort both and compare — O(n log n). Or count characters in a dictionary and compare counts — O(n). Offer both and say which you would ship.

Incident management

2 questions

Reported as “Incident management” and as a specific scenario: a Web API suddenly returning 500s in production.

A Web API suddenly starts returning 500s in production. How do you approach it?

The word suddenly is the whole question. Something changed. Your job is to find what, and the order of your steps is what is being graded.

1. Stabilise before diagnosing

If a deployment went out in the window, roll back first and investigate from a healthy state. Restoring service is not the same as finding the cause, and confusing the two is the most common mistake under pressure. Communicate: who is affected, what you know, when you will next update.

2. Characterise the blast radius

  • All endpoints or one? One points at a code path; all points at a dependency or infrastructure.
  • All tenants or one? One tenant points at data or configuration specific to them.
  • All instances or one? One points at that host — disk, certificate, a failed deploy.
  • What is the error rate? Intermittent suggests resource exhaustion or a race; total suggests a hard dependency failure.

3. What changed in the window

Deployment, configuration change, feature flag, certificate expiry, dependency release, a data migration, a scheduled job, or a traffic spike. Line the change log up against the error onset timestamp.

4. Read the actual exception

A 500 is a category, not a cause. Pull the exception type, message and stack from structured logs, filtered by correlation ID so you can follow one failing request end to end. Common culprits in order: a null reference on an unexpected payload shape, a database timeout or deadlock, connection pool exhaustion, an expired secret or certificate, a downstream 500 you did not handle, and out-of-memory.

5. Fix, verify, then write it up

Confirm the error rate returns to baseline. Then a blameless postmortem with a timeline, root cause, and specific actions — including the monitoring gap that let it reach users before you noticed.

Make it concrete

Tie this to real debugging you have done: structured JSON logs with a correlation ID, daily rolling files with retention, separate hosts to isolate. Interviewers can tell the difference between a process someone has read about and one someone has used at 2am.

What does good logging and observability look like?

Three pillars: logs (what happened), metrics (how much, how often), traces (how one request moved through the system). You need all three; logs alone cannot tell you where the latency went.

Logging that is actually useful

  • Structured, not string-concatenated — log an event with named properties so it can be queried. _logger.LogWarning("Refresh failed for {TenantId} after {Attempts}", id, n), not an interpolated sentence.
  • Correlation ID on every entry, propagated to downstream calls. Without it you cannot reconstruct a single request.
  • Levels used honestly — Error means someone should look; Warning means it self-healed; Information is flow. Everything logged as Error means nothing is.
  • Never log secrets — tokens, passwords, personal data. Logs get shipped and indexed.
  • Retention and rotation — daily rolling with a fixed window, so a disk never fills at the worst moment.

On the metrics side: request rate, error rate, duration percentiles — p95 and p99, never the mean, because the mean hides exactly the tail your users feel.

How do you deploy and configure a .NET app on IIS?

Generative AI & semantic search

4 questions

Reported in detail: generative AI project experience, explain semantic search, how embeddings and tokens were created, how similarity scores are computed, plus understanding of RAG, LLMs and agent creation.

Explain semantic search — how is it different from keyword search?

Keyword search matches characters. Semantic search matches meaning.

Lexical search (BM25, SQL LIKE, full-text indexes) scores documents by term overlap. A query for “lift installation” will not match a document saying “elevator fitting”, because no term is shared. Semantic search maps both into a vector space where closeness means similar meaning, so the match happens anyway.

The pipeline, end to end

  1. Chunk the source into units small enough to be about one thing.
  2. Embed each chunk into a fixed-length vector with an embedding model.
  3. Index the vectors — a vector database, or an approximate nearest-neighbour index like HNSW or IVF.
  4. Embed the query with the same model.
  5. Search for nearest neighbours by cosine similarity.
  6. Filter and rank — apply metadata constraints, optionally re-rank the top results with a cross-encoder.
The part worth volunteering: narrowing before scoring

Comparing every query against every candidate is the naive design. If your data has a natural partition key, scope the comparison to the matching partition first and the candidate set collapses — each record is compared only within its own group rather than against the whole set. Metadata filtering and hierarchical indexing are the general forms of this. It is also the honest answer to “how does this scale”, which is the follow-up.

Hybrid search — the answer that shows production experience

Pure semantic search is bad at exact identifiers — part numbers, error codes, names. Production systems run lexical and vector search together and fuse the rankings. If asked what you would improve, this is the strongest thing to name.

How did you create embeddings, and what are tokens?

Tokens

Models do not read characters, they read tokens — sub-word units produced by a tokeniser such as byte-pair encoding. “Unbelievable” might become un + believ + able. This matters practically for three reasons: context limits are counted in tokens not characters, billing is per token, and non-English text and code typically consume more tokens per character.

Embeddings

An embedding is a fixed-length vector of floats — commonly several hundred to a few thousand dimensions — produced by a model trained so that semantically similar inputs land close together. The model is the why; the vector is just the output.

What to say about how you built them

  • Chunking strategy — size and overlap, and whether you split on structure rather than raw character count. This is the decision that most affects quality, so lead with it.
  • What text went in — for structured records, the concatenation of the fields that carry meaning, not the raw row.
  • Batching — embeddings are generated in batches against a rate-limited API, with retry and backoff.
  • Storage — where the vectors live and alongside which metadata, because the metadata is what you filter on.
  • Re-embedding — when source data changes, and the fact that changing the embedding model invalidates the entire index. Vectors from two different models are not comparable.
Dimension mismatch

A common interview probe: “What happens if you change embedding models?” Everything must be re-embedded. Vectors from different models occupy different spaces, and cosine similarity between them is meaningless noise — not merely less accurate.

Reference Embeddings guide — OpenAI platform docs Understand embeddings — Azure OpenAI
How do you compute the similarity score?

Cosine similarity — the cosine of the angle between two vectors. It measures direction, ignoring magnitude, which is what you want when document length should not affect relevance.

cos(A,B) = (A · B) / (‖A‖ × ‖B‖)

A · B  = Σ aᵢbᵢ            (dot product)
‖A‖    = √(Σ aᵢ²)          (Euclidean norm)

Range is −1 to 1. For typical text embeddings, values cluster well above zero, so a raw score of 0.7 is not “70% similar” in any absolute sense — thresholds must be calibrated against your own data.

Cosine similarity calculator

The alternatives, and when they matter

  • Dot product — cheaper, and identical in ranking to cosine if your vectors are already normalised to unit length. Many models return normalised vectors, so this is the common production choice.
  • Euclidean (L2) distance — magnitude matters; smaller is better rather than larger.
Confidence banding

A raw score is not a decision. The production pattern is to band it: auto-accept above a high threshold, queue for human review in the middle, reject below. That way the uncertain cases surface instead of being silently guessed. If you have built this, say so — it is a maturity signal that distinguishes a demo from a system.

Explain RAG, and what an agent is

RAG — retrieval-augmented generation

Retrieve relevant context from your own data, put it in the prompt, and have the model answer from it. It exists to solve three problems: the model does not know your private data, its training has a cutoff, and it will invent an answer rather than admit ignorance.

  1. Ingest — chunk, embed, index.
  2. Retrieve — embed the question, fetch top-k chunks, filter by metadata the user is allowed to see.
  3. Augment — build a prompt containing those chunks and an instruction to answer only from them.
  4. Generate — with citations back to the source chunks.

The failure modes to name, because they are what the follow-up is about: retrieval returns nothing relevant and the model answers anyway; chunks are too small and lose context, or too large and dilute it; top-k is too high and the real answer gets lost in the middle of a long context; and access control is skipped at retrieval time, so the model cheerfully summarises a document the user should not see.

Agents

An agent is an LLM given tools and a loop: it decides which tool to call, reads the result, and decides what to do next, until the task is done or a limit is hit. The model supplies reasoning; the tools supply real capability — a database query, an API call, a file write.

  • Tool definitions — name, description, parameter schema. The description is effectively the prompt that decides whether the tool is used correctly.
  • The loop — call, observe, decide. It needs a hard iteration cap or it can run indefinitely.
  • Boundaries — anything destructive should require confirmation, and tool output must be treated as untrusted data rather than instructions. Prompt injection through retrieved content is a real attack, not a hypothetical.
If you have not built an agent, say so

Claiming agent experience you do not have is the fastest way to lose an interview, because the follow-ups get specific immediately. “I have built semantic search and RAG; I understand the agent loop but have not shipped one” is a strong, honest answer — and the reported requirement is understanding, not production experience.

Project & architecture

3 questions

Reported as “Explain your current project and your role in that”, plus the whole L2 round being architecture-focused. This is the round with the most marks available.

Explain your current project and your role in it

Everything in L2 branches from this answer, so structure it deliberately and keep it to about ninety seconds before pausing for questions.

Five beats

  1. Domain in one sentence — what the product does, in words a non-specialist understands. Skip internal names.
  2. Your scope — which part you own, and whether you lead. “I lead three developers on X” sets the altitude for every following question.
  3. Architecture — the four or five boxes and what flows between them. Be ready to draw it.
  4. One hard problem — the thing you would still be proud of. Give the constraint, the options, your choice, and the trade-off.
  5. Scale and shape — tenants, data volume, request pattern. Real numbers if you have them, honest qualitative shape if you do not.
Pre-load three specifics

Have ready: the largest dataset you process, the trickiest concurrency or consistency problem you solved, and one decision you would now make differently. That last one is asked more often than people expect, and “nothing” is the wrong answer — it reads as either inexperience or defensiveness.

Do not oversell

If your product serves a selected set of enterprise clients rather than millions of users, say so and pivot the scale story to where it is genuinely impressive: data volume per request, integration complexity, correctness requirements, multi-tenancy. Inflated traffic numbers collapse under one follow-up about your infrastructure.

How do you handle multi-tenancy?

If your project description says multi-tenant, this follows automatically.

Isolation models, cheapest to strictest

ModelIsolationCostRisk
Shared database, tenant columnLogicalLowestOne missing filter leaks data
Shared database, schema per tenantBetterMediumMigration complexity multiplies
Database per tenantStrongestHighestOperational overhead per tenant

Enforcement, if you share a database

  • Resolve the tenant once per request from the authenticated principal — never from a header or route parameter a caller controls.
  • Apply the filter globally — EF Core query filters — rather than relying on every developer remembering a WHERE clause.
  • Include the tenant in every cache key. A cache without it is a cross-tenant leak waiting to happen.
  • Put the tenant ID on every log entry.
  • Consider noisy-neighbour control: one tenant running a huge job should not degrade everyone else.
The strongest single sentence

“Tenant isolation is enforced in one place, not remembered in many.” A global query filter plus a tenant resolved from the token means a forgotten filter is impossible rather than merely unlikely.

Monolith, modular monolith or microservices — what did you choose?

The trap here is enthusiasm. Advocating microservices for a small team is a negative signal, not a positive one.

What microservices actually cost

  • Distributed transactions become sagas with compensating actions.
  • Every in-process call becomes a network call that can fail, time out, or arrive twice.
  • Debugging needs distributed tracing before it is possible at all.
  • Deployment, versioning and local development all multiply.

A modular monolith — one deployable, strict module boundaries, no cross-module database access — gets most of the structural benefit without the distributed-systems tax. It is also the honest starting point, because the boundaries you would need for services become obvious only after the domain settles.

Extract a service when there is a specific reason: independent scaling, a different technology requirement, a separate team with its own release cadence, or a hard compliance boundary. “It felt cleaner” is not a reason.

If you run a shared platform service

A service consumed by several products is a legitimate microservice with a real reason: independent lifecycle and a contract between teams. That is a far better answer than an architecture-diagram justification, because it names the organisational force that actually drove the split.

HR round

2 questions

Reported as virtual, professional, and clear about role, culture and expectations. Treat it as a real round.

The standard questions, and how to answer them

Why are you looking to move?

Forward-looking, never a complaint. Name what you want more of — scale, a different domain, deeper ownership — rather than what you are escaping. Criticising a current employer reads as a preview of how you will talk about this one.

Walk me through your career

Three minutes, chronological, with the reason for each transition. Where you grew, not just what you did.

Tell me about a conflict or a failure

Situation, your action, outcome, what you changed afterwards. The last part is the whole point. Pick something real with a genuine cost — a sanitised failure reads as evasion.

Where do you see yourself in a few years?

Honest direction, whether that is technical depth or team leadership. If you already lead developers, say which way you want to go and why.

Notice period and availability

Know your exact number and any buyout terms before the call.

What should you ask them?

Having no questions reads as indifference. Four that get real answers:

  • “What does the first ninety days look like for whoever takes this role?” — tells you whether the role is defined.
  • “How do technical decisions get made here — who decides on architecture?” — tells you how much ownership is real.
  • “What is the on-call and incident process?” — tells you about engineering maturity, and signals you have operated systems.
  • “Why is this position open?” — growth or backfill; both are fine, and the answer is informative either way.
On compensation

Know your number before the call, including the breakdown. If pushed early, it is reasonable to ask for the band for the role first. Treat it as information exchange, not confrontation.
